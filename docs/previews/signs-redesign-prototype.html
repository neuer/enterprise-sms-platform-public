    设计决策（相对现网的变更点）

  • 筛选条单行化：状态 seg（全部 / 待审核 / 已通过 / 已拒绝）带计数，与名称关键词输入同行；两者均为全量列表响应的前端推导，不新增查询参数（接口无分页，不过滤时底栏仅「共 N 个签名」）。前端
  • 规范签名列即主列：【名称】作可点击主标题（开详情抽屉），副行只留平台编号；独立「厂商编号」列取消，收进状态列副行。现有
  • 待审核细分双阶段：vendor_sign_id 为空 → 副行「提交厂商中」（同步按钮不出现，避免空轮询）；已有编号 → 「厂商审核中 · #编号」+ 可手动同步。全部由现有字段推导。前端
  • 驳回原因上浮：已拒绝行状态列副行直接显示 vendor_reject_reason（现网为独立「厂商意见」列），修改动线少一步。现有
  • 详情抽屉加审核轨迹：已提交 → 已绑定厂商编号 → 审核结果 三段步骤条，驳回时 verm 块置顶；附「发送效果预览」——签名自动拼接于内容最前、计费长度含签名（前端演示推导，唯一计费实现仍在 services/billing.py）。前端
  • 申请 / 重交抽屉即时反馈：规范化预览（剥离一对外层方括号、去空白）与内联报错跟服务端 format_sign_name 同一规则；「计入每条计费长度 +N 字」实时提示；驳回重交顶部 verm 条回显上次原因，按钮文案「重新提交审核」并如实告知将生成新厂商编号。前端
  • 默认签名引用联查：详情抽屉显示把该签名设为默认的应用（admin 调 GET /admin/apps 现有响应的 default_sign 字段前端 join，仅 admin 发起与渲染；评审不过则整项砍掉，删除 409 仍是服务端最终裁决）。前端扩展
  • 删除确认如实告知：已通过、被应用设为默认签名或已被批次引用的签名不可删除（服务端 409 裁决，按钮显隐只是提示）；删除行为与操作人写入审计，toast 同步提示留痕。现有
  • 角色边界不变：读 operator/approver/admin、写仅 admin；operator/approver 不渲染「申请签名」按钮与操作列。接口响应无创建人与时间戳，界面一律不展示。现有

    契约核对

  • 列表与详情字段全部来自 GET /api/v1/web/signs 现有响应（id / name / vendor_sign_id / vendor_state / vendor_reject_reason）；响应无 created_by / created_at，界面一律不展示。现有
  • 状态计数、关键词过滤、待审核双阶段、审核轨迹、规范化预览与「+N 字」计费提示均为前端推导或确定性演示；规范化唯一实现仍在服务端 format_sign_name，计费唯一实现仍在 services/billing.py（规则 18），前端只做即时反馈、不另造逻辑。前端
  • 「默认签名引用」为前端联查扩展：admin 调 GET /admin/apps 现有响应的 default_sign 字段，不新增接口、不改契约，仅 admin 发起与渲染；评审不过则整项砍掉。前端扩展
  • 角色与数据边界不变：读 operator/approver/admin、写仅 admin；写操作审计沿用 sign_create / sign_update / sign_delete / sign_sync（规则 14）；本页不涉及手机号，无掩码 / 解密边界问题（规则 2）。现有
  • 状态机不变：create 直落 pending 并将 Bind 意图同事务写入 Outbox（realtime worker 持凭据执行 BindSign）；update 仅 rejected，重交即置 pending、清空厂商编号与驳回原因并重新入队；delete 受「已通过 / 应用默认签名 / 批次引用」409 约束；sync 仅 pending 返回 202 入队全局同步。现有
