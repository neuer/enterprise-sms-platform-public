    设计决策（相对现网的变更点）

  • 添加收进 440 抽屉：撤下现网顶部常驻的大输入卡，页头右侧「添加号码」主按钮唤起抽屉；textarea 前端实时预检（有效 / 批内去重 / 格式错误行号），与服务端同规则 ^1\d{10}$、同批内 HMAC 去重口径；备注 ≤128 字且不得含号码形态文本；400 报错只带行号、不带号码内容，内联展示。前端
  • 筛选收进单行检索条：来源 seg（全部 / 人工加入 / 回复退订 / 导入，点选即重查）+ 关键词 220px + 查询 / 重置，与上行回复、号码搜索同一语言；隐私说明沉条底，独立筛选卡片取消。黑名单可达数万条，保持服务端分页与过滤，不走「接口全量返回 · 前端过滤」。现有
  • 来源 tag 口径统一：manual→人工加入（verdi）/ reply_optout→回复退订（琥珀）/ import→导入（slate），与号码搜索页徽标映射一致（§7-3a）。现有
  • 总数沉入底栏：页头右侧计数块撤下改为「添加号码」主按钮；底栏「共 N 条 · 每页 20」与分页器同行。前端
  • 移除确认如实告知后果与留痕：移出后通知 / 营销发送不再拦截该号码（验证码本就不拦截，见 category.py）；移除行为与操作人写入审计日志；toast「已移出黑名单 · 本次操作已记入审计」，成功后重查列表。现有
  • 添加结果如实分账：toast「新增 N 个 · 已存在并更新 M 个 · 本次操作已记入审计」，对应响应 added / updated（已存在号码按全版本 HMAC 别名归并后更新来源与备注）。现有
  • 页头副文写明类别策略事实：营销强制拦截、通知默认拦截（应用可关）、验证码不拦截——管理员加黑前即可预判影响面。现有
  • 移动端：与桌面合并为单一数据源卡片流，消除现网双份渲染；空态维持两行规约（一行结论 + 一行出路）。前端

    契约核对

  • 全部数据来自现有 GET/POST/DELETE /api/v1/web/admin/blacklist（admin Bearer），字段 phone_hmac / phone_mask / source / remark / created_at；不新增端点、不新增字段、不加导出与解密入口（规则 2）。现有
  • keyword 服务端 ILIKE 仅作用 phone_mask / remark 且转义通配符；永不匹配明文号码。现有
  • 添加为全版本 HMAC 别名归并 upsert：已存在号码更新来源 / 备注并计入 updated；格式错误 400 INVALID_PARAM 只带行号；remark 含号码形态文本被 400 拒绝。现有
  • 审计 blacklist_add 记 {count, source}、blacklist_delete 记 {count:1}，不含号码列表（规则 21）；确认与 toast 文案如实告知。现有
  • 变更经控制 Redis 锁串行并即时失效缓存，受理读下次重建；缓存不可用 fail-closed 503——界面无额外表达，提交失败时展示结构化错误。现有
  • 页面 admin 专属（PRD 附录 A #11），viewer / operator / approver 无入口；路由守卫与导航维持现状。回复页「退订加黑」仍写入 reply_optout 来源，不在本页重复入口。现有
