现状诊断（当前 ReportView）

  • 汇总只用了 3 个字段：接口 summary 已返回 delivered / failed / unknown，页面只展示消息数、计费条、成功率——失败与未知的绝对量级不可见，unknown 口径说明也无处安放。
  • 趋势图丢失分组维度：筛选选了「按应用 / 按部门」，图表仍把所有维度加总成一条双指标线；维度对比只能靠肉眼扫表，图表和筛选互相割裂。
  • 明细表行数 = 周期数 × 维度数：30 天 × 5 个应用即 150 行平铺，无排序、无占比、成功率是裸数字，低成功率行不醒目。
  • 筛选卡独占一整层，且改完条件必须手动点「查询」，页面内容会悄悄过期，没有「条件已变更」的提示。
  • 导出流程视线断裂：入口在页头、任务状态卡沉在页脚，创建导出后要滚屏才能看到进度。
  • 数据权限口径无提示：operator / viewer 仅见本部门数据，页面没有任何地方说明当前统计口径。
方案 A — 分析工作台（推荐）　SUMMARY → COMPARE → DETAIL

三层递进：KPI 总览（补齐 delivered / failed / unknown）→ 维度对比（趋势按维度堆叠 + 排行榜）→ 明细表（可排序、成功率着色）。 筛选压缩为单行工具条，导出状态改为内联状态条紧跟工具条。 新增 ① 结果构成卡现有字段② 趋势维度堆叠前端推导③ 维度排行（含服务端口径成功率）需接口扩展④ 权限口径标签现有字段。

数据需求（对 GET /reports/stats 的影响）

需求内容来源
现有字段summary.delivered / failed / unknown（接口已返回，页面未使用）；items 全字段；can_export_decrypted；JWT claims 的 role / dept（权限口径标签）两个方案均无需后端改动
前端推导趋势按维度堆叠与 Top N + 其他归并（消息数 / 计费条为加法聚合）；份额占比（加法 + 除法，非成功率口径）；成功率芯片着色阈值（纯展示逻辑）；明细表排序重排对现有 items 做确定性变换，不产生新口径
接口扩展dim_summary: [{dim_value, dim_label, total, total_segments, delivered, failed, unknown, success_rate}]——维度在整个区间的汇总。成功率必须沿用 services/stats.py 口径在服务端算好（硬性规则 28：前端不得自行用 delivered/failed 重算成功率），与 items 同事务同事实源两方案共同依赖的唯一新增项；不加则排行退化为「仅消息数 / 计费条」，成功率列留空

不变量（两方案均保留）

口径页面出现的任何成功率一律取自服务端 success_rate 字段；前端只做加法与占比，绝不自行计算 delivered/(delivered+failed)；unknown 永远单列、不进分母。
导出can_export_decrypted 控制明文勾选；明文导出维持 5 分钟单次 step-up 令牌流；导出文件 AES-GCM 落盘、下载流式解密；报表页任何状态不出现手机号。
约束范围上限 366 天、默认近 30 天不变；operator / viewer 固定本部门口径且页面明示；查询仍为手动触发（改条件给「条件已变更」提示，不自动重查）；移动端保留卡片式明细列表。
