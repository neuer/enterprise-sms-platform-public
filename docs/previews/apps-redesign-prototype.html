    现状诊断（为什么这是最痛的一个模块）

  • 卡片网格无检索：名称/部门/类别/状态全靠肉眼扫；迁移收口期几十上百个接入方，定位一个应用要滚完整页。
  • 密钥生命周期黑盒：库里已有 api_key_prefix / api_key_prev_prefix / api_key_prev_expires，但 App 响应不投影 → 卡片只能贴一个死的 sk-••••；「作废旧 Key」按钮常驻，该应用没有宽限期旧 Key 时点了就是 404。
  • 零运行信号：今日消耗 vs 日配额、成功率、限流，卡片上一概没有；配额将耗尽时管理员只能自己去报表页拼条件。
  • 7 个平铺文字按钮：高危（停用 / 作废旧 Key）与低频（接入示例）挤在同一行 footer，无误操作隔离。
  • 12 字段平铺长表单：新建/编辑一个抽屉到底；危险默认值（配额 0=不限、白名单空=全网放行）只有一行细字或局部 alert，创建即生效。
  • 「启用」走整表 PUT 前端重建：把列表行字段原样拼回请求体，任何字段漂移都会静默写坏配置（前端顺带修，不改契约）。前端

    设计决策（相对现网的变更点）

  • 卡片网格 → 单行筛选条 + 账本表格：关键词（名称/部门）+ 类别 seg + 状态 seg；接口本来就全量返回，过滤前端化，不新增查询参数。前端
  • 密钥状态上列：当前 Key 前缀（mono sk-a1b2••••）+ 宽限期倒计时 tag；App 响应补三个非密投影字段：api_key_prefix、old_key_expires_at（null=无宽限旧 Key）、callback_secret_configured。均为元数据，不涉密文，规则 1 不受触碰。契约
  • 今日消耗列：计费条 消耗/配额 + 5px 进度条（>80% 琥珀、≥100% 朱红）；数据来自现有 GET /web/reports/stats?granularity=day&group_by=app 一次联查前端按行合并，成功率口径不动（规则 28）。现有
  • 操作分层：行内只留「详情」；轮换/作废/停用/接入示例全部收进 560 详情抽屉，高危操作仅出现在对应事实旁边并带后果确认。
  • 新建/编辑抽屉三段分组：基本信息 / 配额与策略 / 安全与回调；危险默认值触发组内琥珀警示条（不限量、全网放行），不改变默认值本身（产品默认见 PRD FR-18）。
  • 一次性凭据弹窗保留现有交互：no-store 响应 + 仅展示一次 + 复制 +「我已安全保存」，不重新发明。现有
SCREEN A · 列表全景（筛选条 + 账本表格 · 四种典型状态同行）

    契约核对

  • 列表/详情基础字段全部来自 GET /web/admin/apps 与 GET /web/admin/apps/{id}，无新增查询参数；关键词/类别/状态过滤前端化（沿用签名管理同一规约）。现有
  • 密钥列与详情密钥区需要 App 响应补三个只读投影：api_key_prefix（CHAR(8) 前缀，非密）、old_key_expires_at（api_key_prev_expires 投影，null=无宽限旧 Key，控制「作废旧 Key」显隐）、callback_secret_configured（callback_secret_enc IS NOT NULL）。纯 metadata，不产生/不传输任何密文，规则 1/2 不涉。契约
  • 「创建于」需要 created_at 投影；库列已存在，同样只是响应补字段。契约
  • 今日消耗/成功率：GET /web/reports/stats?granularity=day&group_by=app&start=今日&end=今日 一次联查，前端按应用行合并；成功率口径仍由 services/stats.py 唯一实现，前端不自行计算（规则 28）。现有
  • 轮换 Key / 作废旧 Key / 轮换回调密钥 / 停用 / 创建均沿用现有端点与一次性明文弹窗；「启用」由整表 PUT 前端重建改为先 GET /{id} 取权威配置再 PUT，消除字段漂移写坏配置的风险。前端
  • 凭据与回调密钥明文仍只出现在一次性弹窗的页面易失内存；审计载荷只含操作与引用，不含任何密钥材料（规则 14/21）。现有
