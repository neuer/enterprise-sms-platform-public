现状诊断（当前 BatchView）

  • 「进度」列语义错位：进度条只填 delivered/total，把「送达回执」当「发送进度」。发送中批次回执延迟时进度条长时间低位、形似卡死；待审批 / 定时 / 取消批次恒为 0，该列对一半以上的状态没有任何信息；failed 量在列表完全不可见。
  • 筛选卡 8 个字段平铺独占一层：批次号 / 类别 / 状态 / 测试 / 渠道 / 应用 ID / 部门 / 时间同权重铺开，低频字段（测试发送、应用 ID、部门）常年空置却占据首屏；应用 ID 要求用户手填数字 ID。
  • 发了什么不可见：列表接口已返回 content，页面却不展示；定位「哪个批次发了什么内容」只能逐个开抽屉。verify 内容入库前已经 OTP 等长打码（硬性规则 27），列表展示是安全的。
  • 状态上下文缺失：定时批次的 scheduled_at 在列表不可见（只有创建时间）；deferred_reason（营销窗外转定时）只在抽屉 alert；is_test 无任何视觉标记；重发批次的 resend_of 溯源不可跳转。
  • 抽屉信息松散：donut 构成比占了首屏却只表达三个数，与列表进度条重复；元信息、告警、号码明细、操作平铺一列，560px 内滚动很长；取消 / 改期 / 重发失败无状态显隐逻辑，点了才被 409 顶回来。
  • 操作矩阵从未明示：服务端约束是「仅 scheduled 可取消 / 改期」，界面没有任何地方告诉用户这一点。
方案 A — 账本工作台（推荐）　GROUP → LEDGER → DRAWER

三层递进：状态分组 chips（一眼看到待处理量）→ 构成感知账本表（四段构成条替代单段进度条 + 内容摘要列）→ 分区抽屉（结果概览 / 内容 / 元信息 / 号码明细）。 筛选压缩为单行工具条，低频字段收进「更多筛选」；应用 ID 输入框改为应用名下拉（取自现有应用管理接口）。 新增 ① 状态分组 chips 及计数计数需接口扩展分组为前端推导② 四段构成条前端推导③ 内容摘要列现有字段④ scheduled_at / deferred / is_test / resend_of 列表徽记现有字段⑤ 操作按钮按状态显隐前端推导。

方案 A · 详情抽屉（右侧面板 mock，实现为 el-drawer 560px）

抽屉分四区：结果概览（大构成条 + 四计数 + 计费口径）→ 内容卡（全文 + 类别/打码说明）→ 元信息两列网格（resend_of 可点击跳回源批次）→ 号码明细（状态筛选 + 分页，沿用现有接口与授权查看）。 操作按钮按状态显隐并附原因文案，不再裸等 409；左侧为操作 × 状态矩阵，供评审确认。

操作 × 状态矩阵按钮显隐 = UX 提示，服务端 409 仍为最终裁决

批次状态取消改期重发失败
定时中✓✓—
待审批—（审批中心处理）——
排队中 / 发送中——有 failed 即可
余额阻断——有 failed 即可
已完成——有 failed 即可
已取消 / 已驳回 / 已过期———

依据：SchedulingService.cancel / reschedule 仅接受 scheduled（其余 409 STATE_CONFLICT）；ResendService 不限批次状态、按 failed 明细重建新批次并完整重走频控 / 审批 / 时间窗。写操作仅 operator / admin 可见（canWrite），授权查看仅 approver / admin（canDecrypt）。

需求内容来源
现有字段content（内容摘要列 / 抽屉内容卡）、scheduled_at、deferred_reason、is_test、resend_of、failed、unknown、total、quota_cost、segments、removed_freq_limit、channel、app_name、creator、dept——列表接口已全量返回；应用下拉取自现有应用管理接口，替代手填数字 ID两方案的核心收益均无需后端改动

不变量（两方案均保留）

号码安全列表与抽屉只出现掩码号码；授权查看走既有 decrypt 接口 + 审计；verify 内容入库前已 OTP 等长打码（硬性规则 27），content 展示不产生新的暴露面；审计载荷不含号码（规则 21）。
口径批次域只表达「构成」，页面任何位置不出现成功率；构成条与计数旁固定标注「非成功率」，成功率归统计报表页且取服务端 stats.py 口径（规则 28）。
