# 运行观测事件保留与累计指标

`worker_lease_event` 与 `send_db_failure_event` 是无 PII 的运行观测。
`runtime_event_retention_days` 默认 30，合法范围 1–365 天；管理员通过现有 sys_config
入口修改，保留原有审计与版本校验。无效或损坏配置使压缩失败，不按零天清理。

每日 housekeeping 把这两个事件流加入固定轮转。每页默认最多 500 行（代码上界 1000），
整个轮次最多 64 页和 30 秒，数据库页锁等待 1 秒、语句期限 5 秒。仍有工作时按现有
机制在 30 秒后续作。各页单独提交；失败仅回滚当前页，下一次从剩余过期明细继续。
调度、数据库或续作投递故障会留下积压，因此配置天数不是物理存储硬上限，也不能证明
生产清理已执行。验收需检查 housekeeping 的成功记录、处理条数、剩余明细年龄及数据库容量。

`compact_runtime_events` 只接受两个固定事件流。数据库再次校验保留期、截止时间和页大小，
按 `(created_at,id)` 索引选取过期行并 `FOR UPDATE SKIP LOCKED`。实际删除返回的行分组累加到
各自的 `*_rollup` 表，两个步骤在同一事务，不能分开重试。并发者仅累计自己成功删除的行；
临时被其他事务锁定的明细由后续运行恢复，不为清理强制取消业务事务。

累计表只有原有固定枚举维度，worker 最多 55 行、发送数据库故障最多 10 行。
`sms_worker_lease_events` 和 `sms_send_db_failures` 保留现有 Gauge 类型、名称及标签，
值仍表示成功持久化的历史累计事件数。reader 用一条 SQL 的一致快照合计累计表和在线明细，
避免压缩提交恰好处于两次查询之间导致漏计或双计。尚未归档的积压仍会增加查询成本；
数据库故障导致原事件没有保存的缺口仍由 `send_db_observation_unavailable` 日志说明。

七个运行角色不能直接修改或删除观测明细，也不能写累计表。仅 `sms_send` 对固定
SECURITY DEFINER 函数拥有 EXECUTE；`sms_metrics` 只有必要聚合列 SELECT。
本入口不处理 audit_log、短信状态、配额、Outbox 或 raw 重放事实。

0128 是前滚迁移。空归档可以继续既有降级保护；任一累计表已有正计数时，Alembic 降级拒绝，
因为旧 reader 只数明细，会隐藏已经压缩的历史。首次压缩后恢复必须使用兼容累计表的应用。
不能把它标为保证旧 reader 可回退的 expand 变更，不能绕过正式发布对迁移与回退兼容性的检查。
正式 Registry manifest 的生成与解析必须拒绝跨越 0128 的代际声明，避免把压缩迁移误认作
可补偿旧应用的 expand；本变更不开放新的生产 cold cutover 路径或扩大 schema v2 迁移闭集。
应用镜像回退不代表 schema 或指标合同已经恢复，更不允许为回退清空累计表。
